Crowd Detection System

A computer vision pipeline that finds people in a video stream, decides which of them constitute a crowd, and logs only the gatherings that persist — so an operator sees sustained events rather than every passing group.

Overview

The pipeline runs frame by frame over a video source. For each frame it detects every person, reduces each detection to a single centre point, measures the distances between those points, and asks whether enough of them are close enough together to count as a crowd.

A single frame is not enough evidence, so the system also tracks whether a crowd holds across consecutive frames. Only gatherings that survive that check are written to crowd_log.csv with the frame number and the size of the largest group.

All three thresholds — minimum crowd size, proximity distance in pixels, and persistence window — are constants at the top of the file, so the same code adapts to a narrow corridor or an open concourse by changing numbers rather than logic.

The Problem

Crowd density is a safety problem before it is a technical one. Crushes at stations, venues and religious gatherings develop over minutes, and the people best placed to intervene are usually watching a wall of camera feeds where nothing looks unusual until it is too late.

Counting people is the easy half and largely solved by off-the-shelf detectors. The harder half is judgement: a detector that reports "eleven people are visible" says nothing, because eleven people spread across a plaza is a normal afternoon and eleven people pressed into one doorway is an incident.

So the real requirement was to convert raw detections into events worth alerting on — which means encoding both spatial closeness and duration, and suppressing everything else.

Approach

STEP 01

Detect, then discard

YOLOv8-nano runs on each frame and every detection that is not class 0 (person) is dropped immediately. The nano weights were chosen over larger variants because the pipeline is meant to keep up with a live feed, and detection accuracy on people at this scale is adequate.

STEP 02

Bounding boxes to centroids

Each surviving box is collapsed to its centre point. Reasoning about proximity between boxes means dealing with overlap, size and aspect ratio; reasoning about points means one Euclidean distance. This is the simplification that makes the rest of the logic tractable.

STEP 03

Proximity clustering

Centroids within 50 pixels of each other are gathered into a group, and a group of three or more is treated as a crowd. Members of a counted group are marked as visited so they cannot be double-counted in another group within the same frame.

STEP 04

Temporal persistence

Frames containing a crowd are accumulated, and only when a crowd has been present across a 10-frame window is an event logged. This is the filter that separates a queue forming from three people happening to walk past each other. After logging, the accumulator is cleared so one long gathering does not produce a flood of duplicate rows.

STEP 05

Structured output

Events are streamed to CSV as they occur, with columns for frame number and crowd size, so the output is usable by anything downstream without a bespoke parser. The file is opened once and written incrementally rather than buffered to the end of the run.

Challenges

01

Defining "a crowd" at all

There is no objective threshold. Three people at 50 pixels is a reasonable guess for one camera angle and wrong for another, because pixel distance depends entirely on how far the camera sits from the scene. The honest resolution was to stop pretending a universal constant exists and expose all three thresholds as configuration, calibrated per deployment.

02

Two bugs found reviewing my own code

Re-reading the detector after it was working turned up two defects that testing on a single clip had not surfaced:

  • Grouping under-counts. Each candidate group is built by measuring everyone against a single seed person. A chain of people standing in a line — A near B, B near C, but A far from C — is a real crowd that this logic splits apart. Proper transitive clustering would catch it.
  • The persistence check is too strict. It tests for exact equality against the frame window rather than "at least", so a crowd that produces more qualifying frames than the threshold can slip past unlogged — the opposite of the intended behaviour.

Both are documented rather than hidden. They are listed here because a reviewer reading the source will find them, and because the useful skill on display is auditing your own working code, not shipping something flawless first time.

03

Failing without crashing

A missing video file and an unreadable codec are both routine in practice. Each is checked explicitly, reports what went wrong and how to fix it, and still writes a valid CSV with headers so downstream consumers are not handed a missing file.

Result

What works

  • End-to-end detection on real video
  • Persistence filtering suppresses transient groups
  • CSV event log usable by other tools
  • Thresholds tunable per camera

Known limitations

  • Clustering is non-transitive — splits chains
  • Persistence check uses exact equality
  • Pixel thresholds ignore camera perspective
  • No identity tracking between frames

As a prototype it does what it set out to do: turn a video feed into a short list of moments a human should look at. The next version needs transitive clustering, a corrected persistence comparison, and perspective correction so that pixel distance maps to real-world distance.
