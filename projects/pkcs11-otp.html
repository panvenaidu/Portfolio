PKCS#11 OTP Authentication

A working hotel booking site whose login is protected by one-time passwords generated inside a hardware security token rather than by application code — so the signing key never exists in the web server’s memory.

Overview

The visible half is a complete booking application: room listings and detail pages, a booking flow with confirmation, user profiles, contact and facilities pages, PDF generation for confirmations, and a MySQL schema shipped as pkhotels.sql.

The interesting half is the authentication. Instead of computing a one-time password in PHP, the application delegates generation and verification to a cryptographic token accessed through PKCS#11 — the same interface used to talk to smart cards and real hardware security modules. SoftHSM provides that token in software so the design can be built and tested without buying hardware.

The Problem

Passwords alone are weak, so a second factor is standard. But bolting a one-time password onto a web app usually moves the problem rather than solving it: the secret used to derive the codes ends up sitting in application config or the database, where anything that can read the filesystem can read it too.

If an attacker gets that seed, they can mint valid codes forever and the second factor is worthless. The requirement was therefore not "add an OTP" but "add an OTP whose key the web application itself is never allowed to see".

Approach

STEP 01

Put the key somewhere the app cannot read it

A PKCS#11 token holds the key material and exposes operations, not secrets. The application asks the token to produce or verify a one-time password; the key stays inside and is never returned. Compromising the PHP layer therefore does not hand over the ability to forge codes indefinitely.

STEP 02

Use SoftHSM as the token

SoftHSM implements the PKCS#11 interface in software. It behaves like a hardware module — slots, tokens, PINs, objects — so the integration is written against the real standard. Swapping in physical hardware later is a configuration change rather than a rewrite.

STEP 03

Initialise slot, token and PINs deliberately

The token has to be initialised before anything works: a slot is configured, the token labelled, and a user PIN and security-officer PIN set. These are setup steps with security consequences, not boilerplate, so they are documented rather than scripted away.

STEP 04

Control access at the operating-system level

Apache runs as its own unprivileged user, which by default cannot reach the HSM device files. Access is granted by placing that user in a specific group rather than loosening permissions globally — the web server gets exactly the access it needs and nothing more.

STEP 05

Deliver the code out of band

The generated password is emailed to the user through SMTP, with the mail credentials supplied by an untracked environment file. The code travels over a channel separate from the browser session, which is the point of a second factor.

Challenges

01

The PKCS#11 helper programs are not in this repository

The setup guide includes a step to compile the PKCS#11 programs, but those C sources are not part of the published repository — what is here is the PHP application, the schema, and the installation guide. Anyone cloning it gets a working booking site and the documented HSM procedure, not a one-command build of the cryptographic layer. This is the honest state of the project and the first thing worth fixing.

02

Permissions are where HSM integrations actually fail

Most of the difficulty was not cryptographic. The token is visible to the shell user who created it and invisible to the Apache user, so the code works when tested from a terminal and fails silently through the browser. Getting group ownership and slot configuration right — and understanding why it failed — was the bulk of the work.

03

A setup with many moving parts needs real documentation

SoftHSM, Apache, PHP, MySQL, token initialisation, group permissions and SMTP all have to line up before a single login succeeds, and any one of them failing looks identical from the browser. A step-by-step installation guide ships with the repository because without it the project is not reproducible — and a project nobody else can run is not finished.

Result

What works

  • Full booking flow with confirmation and PDF
  • OTP generated and verified inside the token
  • Key material never enters PHP memory
  • Documented, reproducible setup procedure

Known limitations

  • PKCS#11 helper sources not in the repository
  • SoftHSM is a software token, not real hardware
  • No TLS configured in the shipped setup
  • Single-server design; no key backup or rotation
