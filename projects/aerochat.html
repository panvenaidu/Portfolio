Overview

The assignment was about container orchestration, so that is what this repository contains: a docker-compose.yml that brings up a chat application as four cooperating containers, a Makefile wrapping the lifecycle, a deploy script, and an example environment file.

The application source itself is kept private and is not published here, and nothing is hosted — the stack runs on a local machine and nowhere else. What is on show is the infrastructure definition, which is what the exercise was marked on.

The Problem

A web application that needs a database and a cache is four moving parts, not one. Running them by hand means installing PostgreSQL and Redis locally, starting each in the right order, remembering the connection strings, and hoping the next machine is configured identically.

The classic failure is "works on my machine": versions drift, a service is missing, or a port collides. Containers exist to make that reproducible — the same declaration produces the same stack anywhere Docker runs.

Approach

STEP 01

Declare the whole stack in one file

Four services are defined together: a React frontend on port 3000, a Node backend on 5000, postgres:15 and redis:7. Two are built from local Dockerfiles, two are pulled as pinned upstream images, so nothing depends on what happens to be installed on the host.

STEP 02

Give them a private network

All four join a single app-net bridge network. Containers reach each other by service name — the backend connects to redis://redis:6379, not to an IP — and only the ports deliberately published are reachable from outside. The database and cache are never exposed to the host at all.

STEP 03

Make the data outlive the container

Containers are disposable; the database must not be. A named volume, chat_pgdata, is mounted at the PostgreSQL data directory so a rebuild or restart keeps existing data. Wiping it is a separate, explicit action.

STEP 04

Keep configuration out of the image

Credentials and connection strings come from an env_file at run time rather than being baked into a layer. An .env.example is committed so anyone can see which variables are required, while the real .env stays out of version control.

STEP 05

Reduce it to one command

A Makefile wraps the day-to-day operations — make up builds and starts everything detached, with ps, logs and down for inspection and teardown. A deploy.sh script does the same for anyone who would rather not use Make.

Challenges

01

Startup order is not readiness

depends_on controls the order containers are started, not whether the service inside is ready to accept connections. PostgreSQL takes a moment to initialise, so a backend that connects immediately can fail against a container that is technically already running. The backend exposes a health-check endpoint so readiness can be observed rather than assumed; a proper fix is a health-check condition or a retrying connection.

02

Secrets in a public repository

The setup notes carry a default database password so the stack runs out of the box. That is a real hazard once a repository is public — a default that is never changed is the same as no password. The committed file is an example rather than the live configuration, and the correct habit is to generate credentials per environment and keep them only in the untracked .env.

03

Clean teardown versus keeping data

Stopping the stack and destroying it are different intentions and needed different commands, because conflating them loses the database by accident. make down stops the containers and leaves the volume; only make clean removes the volume with it.

Result

What works

  • One command brings up all four services
  • Service-name networking, no hardcoded IPs
  • Database survives restarts and rebuilds
  • Configuration by environment file
  • Pinned upstream image versions

Known limitations

  • Application source is private, not in the repo
  • Local only — nothing is deployed or hosted
  • No TLS; ports are plain HTTP
  • Startup ordering has no readiness gate
