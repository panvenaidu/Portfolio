Valorix

A performance analytics platform for VALORANT players – match history, agent-level insight and progression tracking. Built as a long-term product rather than a coursework exercise, and still in active development.

Overview

Valorix is a web application that turns raw VALORANT match data into something a player can act on: which agents actually perform on which maps, where a session started to slip, and how form moves over weeks rather than single games.

What is live today is the full product surface – the marketing site and a complete, navigable preview of the product at /vision, covering dashboard, match history, profile, analytics, insights and progression screens. The interface is real and built to production standards. The data behind it is not yet live, for a reason covered below.

The project is treated as a long-running product build. Architecture, design system and component library were established first so that features can be added without rework, rather than shipping a single throwaway page.

The Problem

In-game statistics tell a player what happened, not why. A scoreboard shows kills and deaths for one match, but no player can see their own patterns across a season from inside the game client.

Third-party trackers exist, but most present dense tables that assume the reader already knows what matters. The gap is interpretation – taking the same underlying match records and surfacing the two or three observations that would actually change how someone plays next.

That framing drove every product decision: fewer numbers on screen, each one earning its place, with charts used to show direction over time rather than to decorate.

Approach

STEP 01

Specification before implementation

Screens were specified in writing first – what each one is for, what a user should conclude from it, and what belongs on it. Writing the spec first killed several features before they cost any code.

STEP 02

Design tokens, then components

A Tailwind v4 token layer defines colour, type and spacing centrally, with a deliberately small and low-saturation accent set so the brand red stays dominant. Primitives (GlassCard, StatCard, Section, BrowserFrame) are built on those tokens, so a spacing or palette change propagates everywhere instead of being retyped.

STEP 03

Charts built by hand

Every visualisation – LineChart, Sparkline, SegmentedBar, BarList – is hand-rendered SVG with a shared geometry helper. The dependency list contains no charting library at all: only next, react, framer-motion, animejs, clsx and tailwind-merge.

STEP 04

Data layer isolated from UI

All preview content lives in a single typed module, lib/preview-data.ts, behind the same interfaces a live API would satisfy. Components never know where their data came from, so swapping placeholder records for real ones is a data-layer change, not a rewrite.

Challenges

01

The production API key – the blocker

Live match data requires a production API key from Riot Games. Development keys expire on a 24-hour cycle and are rate-limited to a level no real user base can sit behind, so they cannot back a deployed product.

Production approval requires an application describing a working product with a real audience. That approval has not come through, and it is the single reason Valorix is not serving live statistics today.

How it was handled: rather than stall the project, the product was built to be complete and convincing behind a typed data boundary. Every screen, interaction and chart is finished. Granting the key becomes a data-source swap rather than months of remaining work.

02

Honest placeholders

Preview data is documented in-file as invented. Map and agent names are the real ones so screens read correctly, but handles, ranks, scores and win rates are fabricated and labelled as such, and no Riot artwork or portraits are referenced anywhere. The alternative – unlabelled fake numbers that look live – would have been misleading.

03

Motion without accessibility cost

Scroll-linked animation carries the product story, but unguarded motion is a genuine accessibility problem. Every animated component sits behind a prefers-reduced-motion guard, and entrance animation is centralised in one hook so no component can quietly ship unguarded.

04

Building on a moving target

Next.js 15, React 19 and Tailwind v4 are recent enough that established patterns and much online guidance are out of date. Several conventions had to be taken from the shipped framework documentation rather than from memory or tutorials.

Where It Stands

Shipped

  • Live on Vercel with GitHub CI/CD
  • Seven product screens, fully navigable
  • Reusable component library and token system
  • Charts with zero external dependencies
  • Strict TypeScript, ESLint and Prettier enforced

Next

  • Riot production key approval
  • Live match ingestion behind the typed data layer
  • Player accounts and persistence
  • Insight generation from real history

The honest summary: this is a finished front end waiting on third-party access, not an abandoned prototype. The work that remains is integration, and the codebase was structured specifically so that integration stays small.
